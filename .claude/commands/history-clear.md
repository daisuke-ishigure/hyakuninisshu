# 履歴クリア手順

## これは何か・いつ使うか

このサイトは動画（mp4/mov）を`img/`直下などに直接コミットする運用のため、動画を差し替えるたびに旧バージョンのファイルがGit履歴（`.git`内のオブジェクト）に残り続け、**ワーキングツリーの実サイズよりも`.git`が何倍も大きくなる**。過去に2回、「現在の状態だけを唯一のコミットとする新しい履歴」に作り直すことでこれを解消している（`履歴クリア`, `履歴クリア: 過去コミットに溜まった動画ファイルの重複を解消`）。

`du -sh .git` が明らかに肥大化してきた（動画を数本差し替えた後など）と感じたら、このスキルを実行する。

**この操作はmainブランチの過去コミットを全て消し、「現在の内容だけの初回コミット」1つに置き換える。** リモート（GitHub）側もforce-pushで書き換えるため、後戻りは基本的にできない操作。だからこそ以下の手順は毎回バックアップと差分検証をセットで行う。

---

## 事故事例（2026-09-12）

このスキルを作る直接のきっかけになった事故：`git switch --orphan temp_branch`を手動で実行した際に操作を中断してしまい、ワーキングツリー上で3019ファイルが「消えた」ように見える状態になった。幸い直前のコミットは`origin/main`にpush済みで、`git restore .`一発で復旧できたが、**バックアップタグを取らずに素手でorphan操作を始めたこと自体がそもそもの原因**。このスキルでは、どの段階で中断しても`git reset --hard`一発で元に戻せるよう、必ず先にタグでスナップショットを取ってから進める。

---

## 事前チェック（必須・省略しない）

以下がすべて満たされていない場合は**中止**し、先にユーザーに状況を確認する。

```
git status               # "nothing to commit, working tree clean" であること
git branch --show-current  # main であること
ls .git/index.lock 2>/dev/null && echo "ロックが残っている。中止して先に原因を確認する"
```

- 作業ツリーに未コミットの変更がある状態でこの手順を始めない（消して良い変更か判断がつかないまま巻き込むと危険）。
- `main`以外のブランチにいる場合は、先にそのブランチの扱いを確認する（このスキルは`main`前提）。

---

## Step 1 — バックアップを取る（最重要・絶対に飛ばさない）

```bash
BACKUP_TAG="backup-before-history-clear-$(date +%Y%m%d)"
git tag -a "$BACKUP_TAG" -m "履歴クリア前のスナップショット" main
git push origin "$BACKUP_TAG"
```

- ローカルタグだけでなく、**必ずoriginにもpushする**。ローカルディスク側の事故（今回のような操作ミス、ディスク障害等）に対して、GitHub側にも同じ状態のコピーを残しておくため。
- 何か想定外のことが起きたら、この時点でいつでも `git reset --hard "$BACKUP_TAG"` で全て元通りになる。

---

## Step 2 — 新しい履歴のルートコミットを作る

```bash
git switch --orphan history-clear-new
git add -A
git commit -m "履歴クリア: <理由を書く。例: 動画ファイル差し替えで肥大化した過去コミットを解消>"
```

- `git add -A`は`.gitignore`に従う。現在untracked扱いの動画（`img/ojima.mp4`, `img/tagonoura.mp4`など、使われていない大容量ファイル）は意図的にコミットされない。これらを次回から追跡対象に戻したい場合は、コミットする前に`.gitignore`を先に編集しておくこと。
- **このコマンドを実行したら、完了（commitまで）するまで他の操作を挟まない・ターミナルを放置しない。** 今回の事故は、この種の操作を始めた後に別の作業に気を取られたことが一因。

---

## Step 3 — 差分検証（新履歴が現状と完全に一致するか確認する）

```bash
git diff --stat main history-clear-new
```

**出力が空であることを確認する。** 何か1行でも差分が出た場合は、`.gitignore`の変化やファイル取りこぼしの可能性があるため、**Step 4に進まず**、原因を調べる（差分の中身を`git diff main history-clear-new`で確認し、意図した差分か判断する）。

---

## Step 4 — mainを置き換える

```bash
git branch -M main
```

（`history-clear-new`ブランチにいる状態で実行すると、現在のブランチが強制的に`main`という名前に変わり、既存の`main`を上書きする。過去2回の履歴クリアと同じ手順。）

```bash
git log --oneline -3     # 新しいmainが履歴1件のみのシンプルな状態になっていることを確認
```

---

## Step 5 — リモートに反映する

```bash
git push -f origin main
```

- GitHub Pagesはこのpushを受けて自動的に再デプロイされる。数分待ってから本番サイト（https://hyakuninisshu.com/ ）が正常に表示されることを目視確認する。

---

## Step 6 — ローカルの`.git`を実際に縮小する

`branch -M`しただけでは古いオブジェクトはまだローカルに残っている（reflogが参照しているため）。実際にディスク容量を回収するには：

```bash
git reflog expire --expire=now --all
git gc --prune=now --aggressive
du -sh .git   # 縮小されたことを確認
```

**注意:** これを実行すると、Step1で作ったバックアップタグ以外の古いコミットはローカルから完全に失われる（届く先がなくなり、GCで削除される）。バックアップタグ自体は`refs/tags/`に残っているので、タグを消さない限りこの操作で失われることはない。

---

## Step 7 — 後片付け（サイト正常性を数日確認できてから）

サイトが問題なく動いていることを十分確認できたら、バックアップタグを整理する（残しておいても実害はないので、急ぐ必要はない）。

```bash
git tag -d "$BACKUP_TAG"
git push origin ":refs/tags/$BACKUP_TAG"
```

---

## 何か問題が起きたときの復旧

どの段階で止まっても、以下でStep1時点の状態に完全に戻せる（`push -f`まで終えている場合はGitHub側もリモートで上書きし直す）：

```bash
git switch main 2>/dev/null || git checkout main
git reset --hard "$BACKUP_TAG"
git push -f origin main   # 既にリモートを書き換えてしまっていた場合のみ必要
```
